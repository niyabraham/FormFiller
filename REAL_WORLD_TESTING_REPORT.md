# Real-world compatibility testing report

Date: 30 Oct 2026. Code under test: `main` at `bc193c3` (PRs #19, #20 and #21 merged), Windows 11, Python 3.12, Playwright 1.64.1,
Chromium 156. Branch `test/real-world-compat`. **No implementation file was changed**; this branch adds a test harness, test
data and this report.

## 1. Summary

FormFiller was run against **10 public demo, template and practice forms** (plus 4 supplemental variants), each with two
existing fictional sources, 28 runs in all. Nothing was submitted.

| | |
|---|---|
| Safety (28 runs) | **0 submit events, 0 clicks on final-action controls, 0 network requests completing during a walk** outside one explicit allow rule (1 relayed read-only GET, no answers carried). Blocked attempts are described in section 8 |
| Precision (10 main forms, 20 runs) | **62%** (10 correct of 16 entered); 50% with the "full" source, 100% with the "tricky" source |
| Coverage | **59%** (10 correct of 17 answerable questions); 55% full, 67% tricky |
| Wrong values in correctly-targeted fields | 0. All 10 correct fills were verified by read-back |
| Abstention | 129 of 135 questions that should stay unanswered did (96%). Attestations ("Agree to Terms", 4 of 4) were never answered |
| Wrong fills | **6, from 2 root causes**: a one-word question matched against a longer key (3), and a page's own search box treated as a question (3) |
| Navigation | A real two-page Vue form was walked (Next, Previous, Next) with the entered answer re-verified; a server-backed wizard step worked only with an explicit allow rule; two wizards stopped on third-party tracking requests or a consent overlay |

Not assessed: filling of custom dropdowns and conditional fields (the approved sources contain nothing to enter into those demo
questions; see section 10). No real company RFI portal was tested.

## 2. Scope and safety rules followed

* Public demo/template/practice pages only; no accounts, credentials, CAPTCHA handling or cookie-banner clicking.
* `submit=True` is never passed. FormFiller never pressed a final-action control (verified independently, section 8).
* Every run used FormFiller's multi-step network guard (`DiscoveryPolicy`), even on single-page forms, so nothing left the
  browser after the walk started. The harness added its own stricter layer (abort every non-GET/HEAD during the walk), logged
  every request with its outcome (finished or failed), and recorded every click and submit event the page saw. A completed
  walk-phase request, a submit event or a final-action click stops the batch.
* Fictional data only. FormFiller's own network guard was not bypassed. The one allow rule (S4) is a single read-only GET.
* "Network isolation" is not claimed to be absolute; `docs/SECURITY_MODEL.md` lists what the guard does not cover. Traffic the
  page generates *before* the walk starts (6 to 153 requests per page load, including ads and analytics) is outside FormFiller's
  control and is reported separately.

## 3. Methodology

**Source data.** `source_full.json`, `source_tricky.json` and `IMPLEMENTATION_PROGRESS.md` do not exist in the repository, its
history, or elsewhere on this machine. With your approval I used existing fictional benchmark sources, unchanged:

* "full" = `benchmarks/heldout/h01_saas_security/source.json` (25 facts: legal name, website, HQ city/state/country, headcount, security facts; no street address, ZIP, general phone or services text)
* "tricky" = `benchmarks/rfi/c07_ambiguity/source.json` (17 facts with traps: company vs subsidiary name and employee count, billing vs mailing address, an applicant's and an account manager's names, three e-mail keys, two revenue years)

**Forms** (`benchmarks/realworld/forms.json`): chosen for being public, needing no account, and being either business-like
(vendor registration, business credit application) or wizard-like (multi-page, custom controls). Public multi-page *business
questionnaires* turned out to be scarce: the two multi-page forms available are a scholarship template and generic wizard demos.

**Ground truth** (`benchmarks/realworld/truth/`, generated by `benchmarks/realworld/make_truth.py`). Policy: *expect an answer
only when the source states exactly what is asked.* Inference (years in business from a founding date), ambiguity (billing vs
mailing address; several distinct e-mails), attestations, and personal questions on non-company forms are expected to stay in
review. To keep the labelling independent of FormFiller's answers, the harness first writes `questions.json` (question text,
type, required, step; **no answers**), the truth was written from those lists and the source files, and it was committed
(`e098728`) before any result was opened. The four supplemental forms' truth was added afterwards, again from their question
lists only.

**Metrics.** *Precision* = correct entered answers / answers entered. *Coverage* = correct entered answers / questions that
have an expected answer. Skipped and reviewed questions are never counted as correct. Inputs that are page furniture rather than
part of the form (a documentation site's filter box) are marked `chrome`: they are not in the question counts, but filling one
counts as an answer entered where none was expected. "Correct" requires the page's read-back to equal an accepted value.

**Supplemental runs** (added after seeing the main results, each answering a specific question):
S1 scholarship with Back re-verification (persistence); S2 SurveyJS wizard with the consent overlay removed by the harness
(setup only, never clicked); S3 and S4 Form.io with the required-question gate opted out, S4 also with one explicit read-only
allow rule.

**Harness defects found and fixed during testing** (disclosed because they touch the numbers): the scorer double-counted
page-chrome fills as unsafe (fixed before any figure here); the harness flagged Form.io's `Next` as a submit click because the DOM
`.type` property defaults to `"submit"` for a button outside any form (the page saw 0 submit events; corrected so the flag
means "this click would activate a form's submission"); and an edit briefly broke the harness's own click tripwire, which a
control test caught before any run used it. None of the 28 runs used a defective version of the safety instrument.

## 6. Precision and coverage

Main matrix: 10 forms x 2 sources = 20 runs, 144 questions (+8 page-chrome inputs), 17 with an expected answer, 127 expected to stay in review.

| set | answers entered | correct | wrong fills | precision | expected answerable | coverage |
|---|---|---|---|---|---|---|
| all | 16 | 10 | 6 | **62%** | 17 | **59%** |
| source "full" | 12 | 6 | 6 | 50% | 11 | 55% |
| source "tricky" | 4 | 4 | 0 | 100% | 6 | 67% |

The 6 wrong fills: `Last` <- `pen_test.last_date`; `Email` <- `security.ciso_email` (twice: vendor and scholarship forms); the docs-site filter box <- `soc2.type` ("Type II", three forms). The two `Email` fills are arguable (the key really is an e-mail address, but a CISO mailbox for a generic contact field); if they were accepted, precision would be 12/16 = 75%. Coverage is limited by construction: both sources are small and contain no street addresses, ZIP codes, phone numbers or services text.

Missed answers (7): `Company Name` and `Business Name` (full source, RW-3), `Country` x2 (RW-3), `Region` (no lexical link to `hq.state`), `Your company's legal name` (tricky: `company.name` lacks the word "legal", a deliberate conservative rule), `Full Name` (tricky: two people in the source).

What-if measurement for RW-1, no repository file changed: with rule A applied in-process, the same 20 runs give precision **77%** (10 of 13), coverage unchanged at 59%, wrong fills 6 -> 3 (the remaining 3 are RW-2).

## 7. Compatibility gaps

1. Custom radio groups (`role=radiogroup` / `radio`) are not filled: 7 controls in 5 of the 10 forms are reported as unsupported (plus 3 file/password inputs on DemoQA and Selenium, which are unsupported by design). Safe, but the largest functional gap on modern form builders.
2. A `<label>` that sits in the field's wrapper without a `for` association is ignored (RW-7).
3. Consent overlays block `Next`, with an unhelpful error (RW-4).
4. Pages whose click handlers fire third-party tracking requests cannot be walked under the default block-all policy (RW-5).
5. Page-furniture inputs outside any form (search/filter boxes) are treated as questions (RW-2).
6. Disabled controls are not itemised in walk mode (RW-9).
7. Not exercised (see section 10): filling of custom dropdowns, date pickers, conditional reveal, a walk longer than 2 pages.

## 8. Safety observations

* **Final actions:** 0 submit events and 0 clicks on final-action controls in all 28 runs. The only clicks made were `Next` / `Previous` on the scholarship form (S1: Next, Previous, Next), `Next` once on the SurveyJS wizard (S2), and `Next` on Form.io (S3: 1, S4: 2). `Submit` / `Complete` controls were present on the pages that have them and were never pressed.
* **Walk-phase traffic:** 0 requests completed outside the explicit rule. The guard blocked, per run: 123FormBuilder 7 (6 POSTs to its events API, SnapEngage error reporter and Microsoft Clarity, plus 1 image GET), SurveyJS S2 2 (Twitter advertising pixels), Form.io S3 1 (GET `examples.form.io/customer/submission`). The harness's own write-blocking layer was never needed, because the guard acted first.
* **Allow rule (S4):** one relayed GET to `examples.form.io/customer/submission` (status 401), `carries_answers: false`. A request that carried an entered value would have been refused by the rule's taint check; none was attempted.
* **Telemetry on fill:** on 123FormBuilder the page posted events to its vendor and to session-analytics services during the walk (which includes filling the fields). Because these runs used the guard, none was sent. A plain single-page `run_form` (no policy, the documented default for single pages) has **no network guard**, so such requests would go out (RW-6).
* **Pre-walk traffic** (page load, before FormFiller starts): 6 (Selenium) to 153 (OpnForm) requests per page, including doubleclick/googlesyndication on DemoQA and Google Tag Manager. Not controlled by FormFiller.
* **Consent banners:** none was clicked. One of them blocks `Next` (RW-4).
* **No credentials or session data** appear in `result.json`, `run.json` or the audit reports (URLs are scheme+host+path; no query strings). Traces were not recorded (off by default). Raw runs, screenshots and request logs are in `output/realworld/` (git-ignored); a compact summary is committed in `benchmarks/realworld/results/2026-10-30/`.

## 9. Reproducible bugs

Reproduce any of them with `python tools/evaluate_realworld.py run --out-dir output/realworld --forms <id> --sources <full|tricky>`
followed by `score`. Severity is my judgement of impact on a real questionnaire.

### RW-1 (High, matching) a one-word question is auto-answered from a longer key
*Steps:* run `formbuilder123_vendor` with source `full`. The question `Last` (a last-name box beside `First`) is answered with
`2026-02-17` from `security.pen_test.last_date`; `Email` on `opnform_vendor` and `opnform_scholarship` is answered with
`ciso@brightloop.io` from `security.ciso_email`.
*Cause:* the score for a single question word against a two-word key leaf is F1(precision 0.5, recall 1.0) = 0.667, above
`MIN_CONFIDENCE` 0.6, and no guard caps it (`retrieve.assess_leaf`). The existing one-word guard
(`test_phase3a_hardening.py:95`) covers a one-word *key*, not a one-word *question*.
*Evidence:* `output/realworld/formbuilder123_vendor/full/{result.json,filled.png}`; the fills have confidence 0.6667, category `medium`, and read back as verified.
*Existing coverage:* none for this shape.
*Smallest fix:* when exactly one effective question word matches and the key leaf has additional unexplained words, cap the score
at `UNEXPLAINED_CAP` (0.5), so it becomes a REVIEW proposal. Measured as a what-if: RFI dev 104 -> 101 correct (coverage 55.2% -> 53.6%, precision unchanged), held-out 109 -> 108 (40.1% -> 39.7%, precision 100%), and the three wrong fills disappear. A stricter second rule (cap questions with at most half their words explained) was also measured and rejected: dev 104 -> 86, held-out 109 -> 101.

### RW-2 (High, discovery) a page's own search box is treated as a question and filled
*Steps:* run `surveyjs_wizard` (or `_conditional`, `_dropdown`) with `full`. `Type to filter the list...` (a documentation
site's `<input id="sidebar-search" type="text">` inside an `<aside>`, outside any form) is typed with `Type II`.
*Cause:* discovery has no notion of page furniture, and the label shares one word with `soc2.type` (two effective words, one explained, which no guard caps). Rule A of RW-1 does not catch it.
*Existing coverage:* none.
*Smallest fix:* treat inputs inside `nav`, `aside`, `header`, `footer` or `role=search|navigation|banner|complementary` that are not inside a `<form>` as not part of the questionnaire (report them as `not_a_question`, do not answer them). Needs a fixture that has a legitimate form inside an `<aside>` to confirm the form exception.

### RW-3 (Medium, matching) the foreign-entity veto turns into REVIEW even though the company's own fact exists
*Steps:* `opnform_vendor` / `opnform_credit` with `full`: `Company Name` and `Business Name` stay in review ("the best matching fact `company.parent_company.name` belongs to a parent"), although `company.legal_name` is in the source. `Country` is reported ambiguous between `company.hq.country` (US) and `company.parent_company.country` (GB).
*Cause:* `plan_question` applies the veto to the top candidate and stops; and a parent's fact still counts as a rival in the ambiguity check.
*Existing coverage:* veto tests exist (`test_matching_layers.py`), but not the fallback to the next candidate.
*Smallest fix:* after the veto, re-evaluate the remaining non-foreign candidates with the normal threshold and margin; exclude foreign-entity candidates from the rival set when the question names no entity. Not measured (needs a benchmark run before it is adopted); costs 4 missed answers today.

### RW-4 (Medium, navigation) a consent overlay blocks Next and the error is opaque
*Steps:* run `surveyjs_wizard`: stop reason `next_click_failed`, detail `Locator.click: Timeout 5000ms exceeded.`; the page's cookie banner (`.v2-class---banner--cookies`) intercepts pointer events.
*Existing coverage:* none (`next_click_failed` appears in no test).
*Smallest fix:* when the click fails with "intercepts pointer events", record a `next_blocked_by_overlay` note naming the covering element's text, and stop. Do not click consent automatically (that is the user's decision); optionally accept a caller-supplied pre-step.

### RW-5 (Medium, compatibility, policy decision) third-party tracking stops a walk
*Steps:* `surveyjs_wizard_nobanner`: after `Next`, the page requests `t.co/i/adsct` and `analytics.twitter.com/i/adsct` (image GETs); the guard blocks them and the walk ends `outbound_request_blocked`. 123FormBuilder behaves the same with its telemetry.
This is the guard doing what it is specified to do, but it makes ad-supported and analytics-instrumented pages unwalkable.
*Smallest fix (needs your decision, it touches the safety design):* an opt-in tolerate list in `NetworkPolicy` for requests that are blocked **and** ignored for stopping purposes (for example image/ping GETs to named analytics hosts, never carrying an entered value); they stay blocked and recorded. Default unchanged.

### RW-6 (Medium, safety) single-page runs have no network guard
*Steps:* `tools/validate_public_form.py` without `--policy`, or `run_form` without a policy, runs unguarded. In this test the same page (123FormBuilder) attempted 6 telemetry POSTs during the walk, which includes filling the fields (whether each is triggered by the fills or by timers was not separated).
*Existing coverage:* documented in the README and `OUTPUT_DESIGN.md`; no test, by design.
*Smallest fix:* a `run_form(..., block_network=True)` option for single pages (reusing the existing guard), and make `validate_public_form.py` use it by default with an opt-out.

### RW-7 (Medium/Low, discovery) labels: unassociated `<label>` and id-like labels
*Steps:* `opnform_vendor`: the phone input is labelled `123-456-7890` (its placeholder) because the "Phone Number" `<label>` has no `for` and the input no id. DemoQA: `dateOfBirthInput`, `subjectsInput`, `react-select-3-input`, `name@example.com`; 123FormBuilder: `c_0000000a`.
*Existing coverage:* COMPATIBILITY.md pins plain text in a preceding `<div>` as unsupported; nothing covers an unassociated `<label>`.
*Smallest fix:* when a control has no label association, use the nearest `<label>` in the closest ancestor that contains exactly one control; and humanise or flag id-like fallbacks (`camelCase`, `*-input`, `c_<hex>`) as "unlabelled" so a reviewer is not shown an id as a question.

### RW-8 (Low, reporting) step headings come from page furniture
`opnform_scholarship` steps are headed "Frequently asked questions" and "Powerful forms for everyone."; SurveyJS shows "Your cookie settings". The audit report's navigation table is misleading.
*Smallest fix:* prefer headings inside the form's container or the `main` landmark; fall back to the first control's section label.

### RW-9 (Low, reporting) disabled controls are not itemised in walk mode
`demoqa_practice` City dropdown and `selenium_webform` "Disabled input" appear only as a `control_stayed_disabled` note; `summary.counts.skipped` is 0 (single-page mode lists them as `skipped`). No test mentions `control_stayed_disabled`.
*Smallest fix:* add them to the items as `skipped` when the walk ends.

## 10. Not assessed, and limits of this test

* **Custom dropdown, date-picker and conditional-field *filling*** could not be assessed: with the two approved sources none of those demo questions (car brand, NPS score, subjects, ...) has an answer, and FormFiller correctly entered nothing. Testing the mechanics would need a purpose-built source with demo-specific facts (clearly labelled as mechanics-only, not company data). This needs your approval, because it creates test facts.
* Only 2 pages of a wizard were ever walked in a real app; multi-step Back/Next persistence has one real-world data point (S1, one value).
* 10 forms, mostly single-page, mostly template pages for form builders: **this is not evidence about real company RFI portals** (authentication, long questionnaires, server-side validation, save-and-resume).
* Ground truth was written by one person (the test author) after the policy was fixed; the pre-registration commit makes it independent of FormFiller's answers, not of my judgement. The two sources are small, so coverage is low by construction and the "full"/"tricky" split is partly an artefact of what each source holds.
* Pages change; these results are for 30 Oct 2026.
